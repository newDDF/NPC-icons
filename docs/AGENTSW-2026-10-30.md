## 1. Project Overview

**Project:** NPC-icons  
**Repository:** https://github.com/newDDF/NPC-icons  
**Live website:** https://icons.x0u0x.xyz/  
**Local development path (macOS):** `/Users/ddf/github/NPC-icons`

NPC-icons is an icon library website built with Astro. It provides searchable icon collections, icon detail pages, customization, previews, and export functionality.

The project is intended to remain lightweight, maintainable, and compatible with static hosting environments such as Cloudflare Pages.

### Core principles

- Preserve existing functionality and visual consistency.
- Prefer incremental improvements over large-scale refactoring.
- Keep the project architecture understandable and maintainable.
- Avoid unnecessary dependencies and runtime complexity.
- Protect existing user work at all times.

## 4. Git and Workspace Safety

This section is mandatory.

### 4.1 Protect existing changes

Before modifying files:

1. Run `git status --short --branch`.
2. Identify modified, staged, and untracked files.
3. Inspect relevant existing changes.
4. Avoid overwriting work that was not created by the current task.

The project may contain local backups, diagnostic scripts, experiments, and unfinished changes. Their presence does not mean they are disposable.

### 4.2 Branch policy

- Do not develop directly on `main` unless explicitly instructed.
- Inspect the active branch before making changes.
- Do not switch branches without checking for uncommitted changes.
- Do not merge, rebase, reset, or rewrite Git history without explicit approval.

The last known development branch was:

`feature/permanent-icon-ids`

This is historical context, not a guarantee of the current branch.

### 4.3 Forbidden operations without explicit approval

Never independently run:

- `git reset --hard`
- `git clean -fd`
- Broad `git restore` commands
- Commands that delete backup directories
- Bulk replacement of project files
- Automatic commits or pushes
- Production deployment

When a rollback is necessary, restore only the exact files and changes that have been confirmed.

### 4.4 Before finishing a task

Report:

- Files changed.
- What was changed and why.
- Commands or tests executed.
- Actual test results.
- Remaining issues.

Do not claim a build, test, push, or deployment succeeded unless its result has actually been observed.

### Data management rules

- Keep metadata consistent with the existing schema.
- Do not invent icon descriptions, sources, or licensing information.
- Avoid introducing redundant metadata fields.
- Preserve existing icon naming conventions.
- Some icons may share similar names but represent different variants.
- Existing suffixes such as `1`, `2`, `black`, and `light` may be meaningful.

### Stable icon IDs

Permanent icon ID management has been an active development topic.

Important decisions from previous discussions:

- The user decided not to add a conventional `id` field to every `config.json` record.
- A permanent ID mechanism was explored separately.
- Existing registry and migration files must be inspected before changing the ID strategy.
- Do not regenerate IDs or rewrite existing mappings without understanding their compatibility implications.

Potentially relevant files discussed previously include:

- `data/id-registry.json`
- `data/legacy-id-map.json`

Their current existence and implementation status must be verified.

**Never assume that an ID migration is complete merely because related files exist.**

## 8. UI and UX Guidelines

The preferred visual direction is:

**Clean, restrained, Apple-inspired frosted glass.**

The project should favor clarity and usability over decorative effects.

### Visual requirements

- Use subtle Gaussian blur and translucent surfaces.
- Maintain clear contrast in both light and dark themes.
- Keep spacing, alignment, and component proportions consistent.
- Preserve existing interaction behavior and animations.
- Avoid excessive gradients, reflections, and decorative highlights.
- Avoid Liquid Glass styling.
- Avoid introducing visual complexity without a clear usability benefit.

### Frosted glass preference

The user prefers matte frosted glass rather than glossy or liquid-looking effects.

Previously discussed blur values were approximately:

- 12px
- 20px
- 28px

These are design references, not mandatory values. Inspect existing CSS variables before introducing new ones.

### Theme consistency

For nested surfaces:

- Light theme: inner surfaces may be slightly darker than their parent.
- Dark theme: inner surfaces may be slightly lighter than their parent.
- Maintain subtle depth without strong visual contrast.

Do not independently redesign individual components in a way that conflicts with the rest of the interface.

### Editing existing interfaces

Before changing a component:

1. Inspect its current HTML structure.
2. Inspect related CSS.
3. Check theme variables.
4. Identify existing responsive rules.
5. Understand the associated JavaScript behavior.

Avoid solving a layout problem with broad CSS overrides when a precise selector or structural adjustment is sufficient.

## 9. Coding and Editing Rules

- Prefer small, targeted modifications.
- Follow the existing coding style.
- Reuse existing utilities and components.
- Avoid unnecessary abstractions.
- Avoid introducing dependencies for trivial functionality.
- Keep code and project documentation in English where practical.
- Preserve existing comments unless they are demonstrably obsolete.
- Do not rewrite entire files to change a small section.

When using automated replacement scripts:

1. Match the exact original content.
2. Verify that the expected match count is correct.
3. Create a targeted backup when appropriate.
4. Abort if the source content differs from expectations.
5. Inspect the resulting diff.

Never silently continue after an unexpected replacement.

## 12. Agent Workflow

Every task should follow this process.

### Step 1 — Understand

- Read this document.
- Inspect the active Git branch.
- Check the working tree.
- Read the relevant source files.
- Understand the existing implementation.

### Step 2 — Diagnose

- Identify the actual problem.
- Trace the relevant code and dependencies.
- Distinguish confirmed problems from assumptions.
- Avoid proposing unrelated improvements.

### Step 3 — Propose

Before significant changes, briefly explain:

- What is wrong.
- Which files need modification.
- What the proposed change will do.
- What existing behavior must be preserved.

For small, low-risk changes, a short explanation is sufficient.

### Step 4 — Modify

- Make the smallest practical change.
- Preserve unrelated user modifications.
- Avoid unnecessary refactoring.
- Keep changes easy to review and reverse.

### Step 5 — Validate

- Run relevant checks.
- Inspect the resulting diff.
- Report actual results.
- Clearly identify anything that remains unverified.

### Step 6 — Stop and Confirm

Do not automatically proceed to the next development phase.

Wait for the user's direction before:

- Committing.
- Pushing.
- Deploying.
- Performing large refactors.
- Deleting backups.
- Changing architectural decisions.
